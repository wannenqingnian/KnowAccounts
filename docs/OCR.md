## 数据规则

- 所有交易属于一个账本；账户和分类必须来自相同账本。
- MVP 使用 CNY，金额按整数分保存，正式交易金额为正数。
- 账户净余额 = 期初余额 + 未删除交易的账户分录合计。
- 支出为负分录；收入和退款为正分录；转账同时写出入两条分录。
- 信用卡欠款使用负净余额，信用卡还款通过转账处理。
- 手动输入仅确定日期，保存 `occurred_date` 和 `time_precision = day`。
- 创建及修改审计时间使用 UTC；设备 ID 和版本字段已预留。
- 修改正式交易时同事务重建分录，删除时保留分录但不参与余额。
- 有有效退款的原消费不允许修改或删除。先删除退款后可操作。
- 恢复退款重新校验原消费是否有效以及累计退款上限。
- 待报销标记不扣减统计；0.13.0起报销到账按到账日期冲减消费净额，不计普通收入。

## 0.2.0 智能输入边界

首页右上角“一句话记账”入口支持输入/粘贴单笔人民币收支。例：“昨天晚上滴滴四十二块五，支付宝付的”生成金额 42.50、商户滴滴、账户支付宝、分类打车和昨天日期。缺失或含糊金额、账户及分类留空，进入确认表单由用户补齐；0.2.0 取消不会写入数据库；0.4.0 起识别草稿持久化，未确认不会形成正式账目。

支持阿拉伯数字、中文口语金额、财务大写、全角数字、千位分隔、日期和订单号排除。基础别名词典仅建议已知商户与分类，未知商户不凭空补充；显式分类关键词优先于商户建议。

多个金额不自动选择，多个可能账户不自动绑定；退款、转账、还款、外币和收支混合描述要求使用手动入口。日期无法识别时显示今天并提醒核对。未知语句仍可能无法正确理解，所有草稿必须由用户确认。

0.2.0 使用 Schema v1；0.3.0 使用 v2；0.4.0 使用 v3，并持久化 RawTransaction、草稿与确认关联。0.5.0 已接入 Android OCR；ASR 和通知仍是接口预留。OCR模型仅主动下载/导入，识别不新增网络调用，确认保存沿用原交易服务。

## 需要真机确认

- Android 和 iOS 的启动、重启后持久化、中文输入、键盘和日期选择。
- 原生文件选择器的保存、读取及用户取消路径。
- 大数据量下列表、逻辑备份耗时及低内存设备表现。
- 杀进程、低存储空间、系统升级及数据库迁移。
- 密码与文件选择器交互没有进入日志；备份错误不覆盖有效数据。

本轮测试只验证单进程本地应用，不证明跨设备并发或所有平台原生插件行为。

## 0.7.0 微信支付账单修复

结构化微信商户账单单独处理标题负号金额、微信零钱/零钱通、支付日期、商户全称、交易单号和底部界面按钮。仅在带支付时间/支付方式/商户字段且“支付成功”的OCR账单上下文中，将“-3.50”解释为3.50元支出；其他负金额文本、多金额、实际退款/转账继续要求核对。

开发机Tesseract分别用三档真实模型运行用户提供的松果骑行截图，均得到350分、微信账户、松果出行、交通及2026-10-04；截图不包含在源码或APK。该结果不是Android真机识别验证。运行此检查需自行传入本地截图及独立模型目录：

```bash
RECEIPT_IMAGE=/path/to/receipt.jpg OCR_REFERENCE_MODELS=/path/to/models flutter test tool/wechat_receipt_integration_test.dart
```
