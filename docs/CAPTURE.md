# Android截图记账（0.10.0）

## 使用

1. 首次在管理页打开“OCR模型与图片导入”，主动下载轻量、均衡或高精度模型。
2. 点击“添加截图记账磁贴”。Android 13及以上会请求系统添加；旧系统或添加未成功时，下拉快捷设置→编辑，把“截图记账”拖入磁贴区。
3. 在支付成功页面下拉快捷设置，点击磁贴。锁屏时先解锁，每次截图均通过Android系统屏幕捕获授权。
4. 知账截取一张图片后立即停止屏幕捕获，打开OCR页面并自动识别；没有模型时等待主动下载，随后识别。
5. OCR完成后自动解析并保存草稿。字段完整、正文文字评分足够且无明显歧义时直接入账，提示“已自动记账”并提供撤销；否则打开核对表单。取消核对时草稿仍在待确认箱；复杂退款/转账回到文字核对入口。

## 实现

- Android API 24+ `TileService`，声明系统 `BIND_QUICK_SETTINGS_TILE`；API34+使用PendingIntent折叠快捷设置。
- 独立透明 `CaptureActivity` 只把请求转交给已连接的知账无障碍服务，随后立即退出并保留原支付页面在前台。
- 无障碍服务通过 Android 单帧截图 API 获取一帧并立即本地 OCR；不包含 `MediaProjection` 权限、录屏授权或截图前台服务。
- `ImageReader`处理行填充，屏幕最多8M像素，PNG写入私有cache/captures/随机UUID文件。先关闭帧、停止projection，再通知Activity打开Flutter。
- MainActivity校验路径必须属于私有captures目录；MethodChannel一次消费路径及采集时间，兼容冷启动和运行中的App。若前次OCR尚打开，新截图待其关闭后再处理。
- 截图离开对应OCR页面后删除；中途进程终止留下的文件在下次截屏时清理超过24小时的缓存。截图不进入SQL或备份，不上传。用户从文件选择器导入的原图不会删除。
- API33+使用`StatusBarManager.requestAddTileService`引导添加；其他系统提供手动编辑说明。

不使用无障碍、悬浮窗或后台持续录屏，不跳过系统屏幕捕获授权。银行等应用的安全页面可能禁止截屏，空白/无文字结果提示改用手动输入。系统保护不能由本App关闭。磁贴截屏不是监听系统截图文件，第三方截图可从文件入口导入。

## 验证与限制

桥接测试验证一次消费、时间保留、无原生插件时启动兼容和添加磁贴请求。界面测试验证有模型时自动OCR、无模型时零自动下载、主动下载后识别、核对前零交易、草稿保留、退出删除临时截图。Android原生服务、Activity、权限和分架构Release编译通过。

没有可用真机/模拟器，不能据此宣称不同厂商的透明窗口、授权弹窗消失时机、通知、截图及低内存行为均已通过。安装后应重点验证：当前支付页面而非知账自身被截图；授权取消不入账；退出/系统停止及时结束；前台通知消失；重复点击不创建持续录屏；受保护页面给出明确失败提示。该版本仍使用开发签名。

参考：[MediaProjection](https://developer.android.com/media/grow/media-projection)、[快捷设置磁贴](https://developer.android.com/develop/ui/views/quicksettings-tiles)。

## 0.7.1 识别改进

原生OCR读取文本行坐标；右上区域出现共享链接/ChatGPT/Cloud等悬浮窗口标记时，只剔除该局部窗口的文字，保留账单金额及下方字段。小尺寸图在8百万像素内放大，稀疏识别漏读“支付方式”值时对标签右侧做单行补识别，仅采用实际读到的零钱/零钱通/微信/支付宝文字。未读到值不猜测付款账户。

结构化微信支付成功账单定位主金额，排除混入的前文及底部操作，且修正本次手机输出中“20264710 4H 15:05:04”的日期易混字符；修正后明确提示核对日期。仍有歧义时可主动进入“手动填写单笔收支”；待确认箱中的同类OCR草稿支持“处理识别问题”继续填写，不沿用不确定金额、账户或分类，也不自动入账。完整手机识别文字回归测试使用替换后的虚构交易单号，用户图片和真实编号不进入源码或安装包。

## 0.8.0 通用识别流程

原生层用文字行的实际位置还原字段和值，避免值略高于标签时倒序。优先稀疏版面；在首轮耗时小于18秒且总45秒预算仍有效时尝试自动版面。不改变已选择模型，也不自动下载其他档位。

对金额、时间、商户和付款账户字段，用标签位置估算值区域，不使用固定屏幕坐标。保留整图、局部原图和局部Otsu二值化的独立文字结果。二值化阈值由每个区域的直方图计算，区域仅在内存中处理；可选补识别到达预算时保留已完成结果。

Flutter层比较候选的字段覆盖，选择较完整原文并补充其他候选缺失的字段；有效金额、日期、账户或商户不一致时，在原文内加入对应校验标记，使重启后的待确认解析仍保留歧义。校验标记必须出现在账单底部操作之前；用户编辑删除标记属于主动纠正。金额冲突不根据分数任选一个数。

通用字段引擎替换旧微信专用模块。金额按实付/付款/交易总额角色分级，优惠、余额、商品价格、交易编号等不参与主金额选择；支付时间优先创建时间。商户可以来自明确字段或付款主金额附近标题，分类只给建议。收入、支出、未付款、退款/转账/借贷和外币分别判断；仍不支持自动保存复杂类型。账户只使用付款字段，平台标题不证明实际出资账户。

使用新微信截图进行开发机图像回归，而不只是复述识别文字；测试从图片识别出1600分、精品沙县小吃、微信零钱和2026-10-03。另有支付宝多金额订单、银行卡消费和超市小票图片回归。手机原生与开发机的渲染和OCR输出可能不同，尚需真机验证。用户截图、真实编号和识别输出不进入源码与APK；仓库只保留匿名生成的图片夹具与替换编号的文字回归。


## 0.28.4 飞桨 PP-OCRv6 结构

当前运行流程替换为：截图 → PP-OCR DB文字检测 → 旋转文字区域透视裁剪 → PP-OCR CTC文字识别 → 几何排序/悬浮窗口过滤 → 通用TransactionParser → 草稿 → 用户核对保存。

Android使用ONNX Runtime 1.23.2和OpenCV 4.12.0，不再依赖Tesseract4Android。PP-OCR模型来自PaddleOCR，使用RapidOCR v3.10.0发布的PP-OCRv6 ONNX转换文件；字符表来自识别模型元数据，不额外下载或猜测字符索引。

| 档位 | 检测模型 | 识别模型 | 下载量 |
| --- | --- | --- | --- |
| 轻量 | PP-OCRv6 tiny | PP-OCRv6 tiny | 6.0 MiB |
| 均衡 | PP-OCRv6 small | PP-OCRv6 small | 29.7 MiB |
| 高精度 | PP-OCRv6 medium | PP-OCRv6 medium | 132.3 MiB |

高精度档的检测和识别均使用medium权重并在设备上离线执行，不上传图片。运行更慢且内存占用更高，不能保证每张图片都比均衡档更准。三个档位都包含检测和识别两份文件，v6统一字符集支持中文、英文、日文、数字及拉丁语系文字；未增加独立180度方向分类模型，EXIF方向旋转和竖直文本裁剪旋转已支持。

模型仍由用户主动下载或从文件导入，不包含在APK、账本备份中。每份文件校验长度和SHA-256；模型清单升级为version=3、engine=ppocr，v4/v5清单不会被当作v6加载。失败安装不会替换完整的当前模型。升级不调整账本Schema、账户ID或分录，界面不增加旧模型迁移提示。

每次识别独立打开并关闭ONNX会话，最多160个文本区域、8百万像素工作图、2048像素识别输入宽度；90秒截止通过RunOptions中断推理，超时不产生正式交易。较小文字行使用动态宽度和归一化零填充，避免全部拉长到320像素。原始截图不离开设备。

日期仅在完整固定宽度MMDD+有效HH:mm上下文恢复缺失的月/日分隔符，必须通过真实日历校验并提示核对；不从交易编号或商户名猜测日期。付款方式中的余额宝、现金等名称不会被同名数值字段截断。

开发机图片参考流程在tool/paddle_ocr_reference.py，采用相同模型、BGR归一化、DB阈值、矩形扩张、透视裁剪、动态填充和CTC解码；用于验证识别到记账草稿的整体过程，不代替Android真机验证：

```bash
PPOCR_REFERENCE_MODELS=/path/to/onnx-models PPOCR_TIER=balanced \
RECEIPT_IMAGE=/path/to/private/wechat-receipt.jpg \
flutter test tool/paddle_receipts_integration_test.dart
```

上文0.7/0.8的Tesseract识别细节仅记录历史实现，当前不再执行。


## 0.9.1 JNI兼容性修复

Release构建完整保留ONNX Runtime和OpenCV的JNI桥接类、构造函数与成员。仅保留native方法不足以覆盖原生反向创建TensorInfo等对象的路径。最终APK需运行tool/verify_ocr_jni_apk.py验证，避免推理返回时被Android以SIGABRT终止。模型下载、识别算法及账单Schema沿用0.9.0，升级无需重新下载模型。


## 0.10.0 直接截图与有条件自动保存

首页“截图记账”调用startCapture启动透明CaptureActivity，再将账本任务移到后台，让之前页面显示在后方。磁贴适合直接在支付账单界面使用；从App首页发起时返回上一应用页面，若上一页面不是账单，不能自动猜测出交易。首次没有模型时截屏仍可保存于本次页面，等待用户主动下载或导入后继续识别。管理页“OCR模型与图片导入”继续用于切换模型、添加磁贴和选择已有截图。

Android每次仍需要系统屏幕捕获授权；仅截取一个帧后停止，不增加无障碍、后台持续录屏或截图上传。

本次用户授权字段完整且无明显歧义时直接保存。canAutoBookkeep要求普通人民币收入/支出，金额>0、明确账户、分类、商户、可解析且不晚于截图的日期、付款/到账成功状态，以及正文各保留文字行的PP-OCR评分至少0.90。该评分是文字引擎分数，不是交易正确概率。缺少原生评分时默认人工核对；界面按钮、服务区文字不作为账单评分。修正了日期分隔符、候选冲突、缺字段等提示都会转人工核对。标题商户仅在清晰重复出现两次时允许自动保存，不依靠商户特例。

自动保存调用autoConfirmDraft：在同一SQLite事务内检查同账本、日期、账户、收支类型、金额和商户（忽略空格/大小写）候选，然后沿用confirmDraft提交交易、分录和来源关联。同一草稿重复回调返回原交易；另一次截图疑似相同交易时保持pending，提示核对，人工可以确认确为另一笔消费。这个保守检查不等于跨来源交易编号去重，也不自动合并真实消费。

成功自动保存后直接关闭处理页，提示金额/商户并提供“撤销”，撤销使用已有软删除与余额重算。截图处理页缩为单个状态卡；原文导入仍先核对文字，避免仅因为导入图片就直接入账。

界面测试覆盖首页直接发起、磁贴handoff、缺模型零自动下载、字段完整自动保存并撤销、重复候选进表单、低评分/无评分人工核对；数据库测试验证并发独立草稿不会自动创建双重分录，关联失败回滚。Android界面授权和将任务移到后台后的实际屏幕内容仍需设备验证。
